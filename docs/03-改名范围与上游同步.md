## 一、改名边界

### 已改为 Chameleon（面向用户的产品标识 + 运行时库名）

| 类别 | 位置 |
|---|---|
| 浏览器标题 / noscript 文案 | `snowy-admin-web/index.html` |
| 系统名称、版权文案、默认重置密码（前端兜底值） | `snowy-admin-web/src/config/index.js` |
| 系统名称、版权、系统描述、默认密码（**数据库种子值**） | `snowy-web-app/src/main/resources/_sql/snowy_mysql.sql` 的 `DEV_CONFIG` |
| 种子账号密码哈希（保持与"默认密码"配置一致） | 同上，`SYS_USER` 中 `superAdmin` / `bizAdmin` 的 `PASSWORD` |
| 应用名 | `spring.application.name=chameleon` |
| 数据库名 | JDBC URL、`application-docker.yml`、`docker-compose.yml` 中 `snowy` → `chameleon` |
| 前端包名/描述 | `snowy-admin-web/package.json` |
| 容器/服务/网络名 | `snowy-web-app/src/main/resources/docker-compose.yml` |
| 项目说明 | `README.md`、`docs/*` |

> **默认密码的连锁关系（重要）**：`SysPasswordUtil.isUserPasswordExpired()` 会用「当前密码 == SM3(系统默认密码配置值)」判断是否过期。
> 因此改默认密码必须**同时**改：`DEV_CONFIG.SNOWY_SYS_DEFAULT_PASSWORD_FOR_B/_FOR_C` 与 `SYS_USER.PASSWORD` 的 SM3 哈希，
> 且前端 `config/index.js` 的 `SNOWY_SYS_DEFAULT_PASSWORD` 兜底值要一致。
> 本项目已按 `Chameleon@2026!` 保持一致：
> `SM3("Chameleon@2026!") = b5833192ccdede23eeb85ef982fb8969b8f30b66ee2a683bbf252b33739606f0`
> （可用 `python -c "import hashlib;print(hashlib.new('sm3','Chameleon@2026!'.encode()).hexdigest())"` 复算。）

### 刻意保留（不建议改）

| 保留项 | 原因 |
|---|---|
| 所有源文件头部的 Snowy 版权与作者声明 | Apache-2.0 与上游条款明确要求"不要删除和修改 Snowy 源码头部的版权声明及出处" |
| `LICENSE`、Knife4j 页脚 `Copyright 2020-2024[SNOWY]` | 出处声明 |
| Java 包名 `vip.xiaonuo.*` | 改动面 820+ 文件，牵动 MyBatis 映射路径、类型处理器包、springdoc 扫描包、代码生成器模板，且**本机无 JDK 17 无法编译验证**；属"高风险、零功能收益"的改动 |
| Maven `groupId/artifactId` 与模块目录名 `snowy-*` | 与包名同因；模块目录名同时被聚合 POM 引用 |
| 配置键命名空间 `SNOWY_*`、`snowy.config.*` | 这些键**同时存在于数据库 `DEV_CONFIG` 与前后端代码**，改名需三处同步且一旦漏改即功能失效 |
| CSS 变量 `--snowy-*`、`snowy-admin-web/src/snowy.js`、`snowy-plugin-biz` 等生成器默认值 | 前端主题与插件注册的运行时契约 |
| logo 图片（`public/img/logo.png` 与 `DEV_CONFIG.SNOWY_SYS_LOGO` 的 base64） | 上游素材，**请替换为你自己的商标**（这是唯一建议你尽快替换的品牌资源） |

### 一句话原则

> 改"用户看到的名字"和"运行时的库名"，不改"代码里的技术标识符"。
> 这样既完成了品牌切换，又保留了与上游逐文件比对的能力。

## 二、如果你的确需要深度改名（包名 / 模块名）

建议单独立项，并在**有 JDK 17 的环境**下边改边编译验证。改动清单：

1. **Maven**：根 `pom.xml` 的 `groupId`、`artifactId`、`<snowy.version>`；4 个聚合模块与 12 个子模块的 `pom.xml`（`<parent>`、`<artifactId>`、`<module>`）、目录名。
2. **Java 包**：`src/main/java/vip/xiaonuo/**` 的目录与 `package`/`import` 语句（含 `snowy-plugin-api` 的跨插件接口）。
3. **资源路径**：`src/main/resources/vip/xiaonuo/**/mapping/*.xml` 的目录与其中 `<mapper namespace="...">`。
4. **配置文件**：`application.properties` 中
   - `mybatis-plus.mapper-locations=classpath*:vip/xiaonuo/**/mapping/*.xml`
   - `mybatis-plus.type-handlers-package=vip.xiaonuo.common.handler`
   - `springdoc.group-configs[*].packages-to-scan=vip.xiaonuo.*`
   - `logback-spring.xml` 中的 logger 名
5. **启动类**：`vip.xiaonuo.Application` 的 `@SpringBootApplication` / `@MapperScan`（如显式指定包）。
6. **代码生成器模板**：`snowy-plugin-gen` 下 `.btl` 模板里的包引用（61 个模板文件含 `snowy` 字样）。
7. **前端**：`snowy-admin-web/src/snowy.js`、`import snowy from './snowy'`、`--snowy-*` CSS 变量、`SNOWY_*` 本地存储键（**注意后端返回的键名也要一起改**）。
8. **验证**：`mvn clean package`、启动、登录、进入系统管理逐页回归（映射文件找不到、Bean 扫描不到、SQL 报 `Invalid bound statement` 是这类改动最常见的翻车点）。

## 三、如何同步上游更新

因为本仓库**没有上游历史**，不能直接 `git merge`。推荐流程：

```powershell
# 1. 加一个只读上游
git remote add upstream https://gitee.com/xiaonuobase/snowy.git
git fetch upstream --tags

# 2. 看新版本相对当前基线到底改了什么
git diff --stat 2c9da36e218901c20cd3b261f33e75b89aeec984 upstream/master
git log --oneline 2c9da36e218901c20cd3b261f33e75b89aeec984..upstream/master

# 3. 只挑你要的提交/文件
git checkout upstream/master -- <path>
```

**避免冲突的小技巧**

- 上游升级时优先"整文件替换"，再重新施加本项目那 9 处品牌改动（见 `README.md` 第七节表格，改动点少且集中）；
- 或反过来：把本项目的品牌改动单独记成一个 patch 文件长期维护。

## 四、后续新增业务代码放哪里

- **业务功能**：`snowy-plugin/snowy-plugin-biz`（B 端）/ `snowy-plugin-client`（C 端）；
- **跨插件调用的接口**：放对应的 `*-api` 模块；
- **系统级能力**：`snowy-common`；
- 也可以仿照现有插件新建 `snowy-plugin-xxx` + `snowy-plugin-xxx-api`，在根 `pom.xml` 与 `snowy-plugin/pom.xml`、`snowy-web-app/pom.xml` 中登记；
- 先用「开发工具 → 代码生成」生成一套 CRUD 再改，是最快的起步方式（上游另有前端示例仓库 <https://gitee.com/xiaonuoadmin/snowy-exm>）。
