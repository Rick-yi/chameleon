# 12 · 性能与容量（多租户大数据量验证）

> 验证目标：模拟「10 个机构，每个机构 500~1000 名学员」的真实形态数据，
> 看系统在多租户 + 大数据量下是否会出现问题，并把发现的问题修掉。

---

## 一、测试场景

| 维度 | 配置 |
|---|---|
| 租户数 | 10 个（scale01 ~ scale10，走真实「租户开通」流程） |
| 每租户学员 | 800 人（3 个校区、8 课程、16 课包、20 班级、12 员工） |
| 每租户订单 | 1,000 笔（800 已付 / 150 待付 / 50 已取消） |
| 每租户课时流水 | 4,000 条（购课入账 + 点名消课） |
| 每租户排课 / 点名 | 240 节 / 3,200 条 |
| 每租户埋点事件 | 20,000 条（页面访问为主） |
| **全库合计** | 学员 8,003、订单 10,011、流水 40,007、点名 32,011、**埋点 200,740** |

压测脚本见 `scripts/perf/`，用法见该目录的 README。

## 二、发现并修复的问题

### 1. 埋点数据没有租户隔离（数据越权 + 慢查询）

- **现象**：某租户只有 2 万条埋点，运营埋点页却显示 6 万条页面访问——统计接口把**全库 10 个租户**的数据都算了进去。
- **原因**：`BIZ_EVENT` 没有登记进租户行级隔离表清单（`GlobalConfigure.TENANT_TABLES`），查询不带 `TENANT_ID` 条件。
- **修复**：把 `BIZ_EVENT` 纳入租户隔离；所有埋点查询自动带租户条件。

### 2. 埋点统计把明细全拉进内存（4 秒 → 120 毫秒）

- **现象**：`/biz/event/summary` 单次 3.9 秒，且随数据量线性劣化。
- **原因**：`summary()` 先把 30 天内的**全部埋点明细** `list()` 到 Java 内存，再在循环里统计。
- **修复**：改为 SQL 侧 `GROUP BY EVENT_CODE, DATE(EVENT_TIME)` 聚合，只回传聚合结果行。

| 接口 | 优化前 p50 | 优化后 p50 |
|---|---|---|
| 埋点统计 `/biz/event/summary` | 3952 ms | **120 ms** |
| 埋点流水 `/biz/event/page` | 510 ms | **82 ms** |

### 3. 新开通的租户拿不到任何接口权限（新机构用不了报表）

- **现象**：新开的租户管理员登录后，菜单能进，但所有报表、导出、自动化接口都返回「无此权限」，
  只有 39 条菜单资源、**0 条接口权限**。
- **原因**：`TenantInitService.copyTemplateApiPermissions()` 在**切换到新租户上下文之后**才去读模板租户的接口权限，
  查出来的是新租户自己的空权限，直接 return。
- **修复**：读取模板权限前先切回模板租户上下文，读取完成再切回新租户。
- **验证**：修复后新开通租户 = 39 条菜单资源 + **92 条接口权限**，与模板租户一致。

### 4. 报表里逐条查名称（N+1）

- **现象**：`教务课消进度` 1.79 秒、`财务校区排行` 0.77 秒；慢查询日志里没有单条慢 SQL——
  说明不是 SQL 慢，而是**一次请求打了成百上千条快查询**。
- **原因**：
  - 课消进度：每条课时账户都单独查一次课程名（800 条账户 = 800 次查询）
  - 财务校区排行：每条消课流水都单独查一次「排课 → 班级 → 校区」（240 条 = 480 次查询）
- **修复**：新增批量接口 `listCourseNameMap` / `listScheduleCampusMap` / `listCoursePackageNameMap`，报表侧一次性取回映射。
  同时把财务统计、课程排行、课消分析里的逐条查询一并批量化。

| 接口 | 优化前 p50 | 优化后 p50 |
|---|---|---|
| 教务课消进度 | 1793 ms | **154 ms** |
| 财务校区排行 | 667 ms | **144 ms** |

## 三、优化后的容量基线

单租户 800 学员 / 1000 订单 / 2 万埋点，稳态（去掉首次 JIT 预热）：

| 接口 | p50 | p95 |
|---|---|---|
| 学员列表（第 1 页） | 38 ms | 57 ms |
| 学员列表（第 80 页 / 深分页） | 25 ms | 30 ms |
| 学员列表（单页 1000 条） | 32 ms | — |
| 订单列表 | 40 ms | 45 ms |
| 收款台（订单 + 退费单 + 统计卡） | 41 ms | 64 ms |
| 课表周视图 | 49 ms | 58 ms |
| 点名消课（课节 + 名单） | 62 ms | 85 ms |
| 财务概览 / 财务看板 | 20 / 39 ms | 26 / 58 ms |
| 财务课消 / 财务校区 / 财务排行 | 68 / 88 / 92 ms | 71 / 101 / 94 ms |
| 教务报表（出勤/满班率/教师负荷/风险学员） | 51~62 ms | 52~75 ms |
| 招生报表（漏斗/来源/跟进排行/试听） | 17~44 ms | 20~47 ms |
| 运营埋点统计 | 125 ms | 143 ms |
| 运营埋点流水（第 2000 页深分页） | 142 ms | — |
| 自动化规则 / 执行记录 | 43 / 16 ms | 43 / 16 ms |

结论：**48 个关键接口在 10 租户 × 800 学员规模下，稳态 p95 均在 150 ms 以内**，页面级首屏（多次请求叠加 + 渲染）稳定在 1 秒内。

## 四、复测方式

```powershell
# 1) 造数
node scripts/perf/scale-tenant-create.mjs
python scripts/perf/scale-data-gen.py

# 2) 压测并比对
node scripts/perf/scale-bench.mjs scale01 3
node scripts/perf/scale-bench-hot.mjs scale01 8
```

若某个接口 p95 超过 500 ms，用 MySQL 慢查询日志定位：

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.2;
-- 压测后查看 D:\data\mysqldata\*-slow.log
```

若慢查询日志里**没有**慢 SQL，但接口仍然很慢，说明是 N+1（大量快查询），
用 `performance_schema.events_statements_summary_by_digest` 按 `count_star` 排序即可看出哪张表被查了成百上千次。

## 五、遗留与后续建议

1. **通知公告（BIZ_NOTICE）是全局表**，没有租户列，多个机构之间公告互相可见。属于上游设计，
   如需按机构隔离要加列并改实体/查询。
2. **埋点流水没有归档策略**：单租户 2 万条/天的量级下没问题，但长期运行建议加「按月归档 + 保留 N 个月」。
3. **报表导出**是同步生成（`export`），数据量大时建议改异步任务（财务域已有 `export/async` 接口，报表域还没有）。
4. **课时账户/流水**按学员维度查询已走索引；若单机构学员数超过 5000，建议对「课时进度」类报表加预聚合。
5. 压测脚本在 `scripts/perf/`，`.jdk/` 下的临时脚本不入库。
