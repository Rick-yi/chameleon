# 05 · 核心业务逻辑细化（课时账务 + 排课联动）

> 本文是 [docs/04](04-教培SaaS产品方案.md) 的深化设计，聚焦整个系统最有价值、也最容易做错的**课时账务（计费）**与**排课**两个核心域。
> 目标：把业务规则、状态机、并发与一致性约束、Service 接口签名定死，再动手写代码。
> 所有金额用 `BigDecimal`（库 `decimal(12,2)`，单位：元），课时用 `BigDecimal`（库 `decimal(10,2)`，支持 0.5 课时，4 位小数运算后按 2 位展示）。

---

## 一、核心域关系总览

```
课包(COURSE_PACKAGE) ──买──▶ 订单(STUDENT_ORDER) ──支付成功──▶ 课时账户(STUDENT_LESSON_ACCOUNT)
                              │                                     ▲
                              │                                     │ 扣减/回补
                              ▼                                     │
 班级(COURSE_CLASS) ──生成──▶ 排课(COURSE_SCHEDULE) ──点名(COURSE_CLASS_ATTEND) ──▶ 课时流水(STUDENT_LESSON_FLOW)
                                                                                    │
                   续费预警(STUDENT_RENEW_WARN) ◀──定时任务扫描──── 账户剩余课时 ─────┘
```

**一句话**：家长买课包 → 进课时账户；老师点名 → 按规则从账户扣课时并记流水；账户余额低 → 系统预警 → 家长续费。排课是"扣课"的触发源，课时账务是钱。

## 二、课时账务细则

### 2.1 课时账户模型（STUDENT_LESSON_ACCOUNT）

- 粒度：**每学员 × 每课程一个账户**（同一学员可同时报美术+舞蹈，账户各自独立）。
- 冗余余额字段 `REMAIN_LESSONS`（= 总课时 - 已用课时），扣课/入账时同事务更新，查询不实时计算（避免大表聚合）。
- 状态 `STATUS`：`正常 / 冻结(退费中) / 已清零`。
- 入账时机：订单支付成功后创建账户（总课时 = 课包课时 + 赠课课时），并写一条入账流水。

### 2.2 报名购课流程（STUDENT_ORDER）

状态机：

```
待支付 ──支付成功──▶ 已支付 ──退费通过──▶ 已退费
   │
   └──超时/手动取消──▶ 已取消（不产生账户）
```

规则：

1. 订单创建时**快照课包价格**（课包后续改价不影响已购学员）。
2. 支付成功后：`改订单状态 → 创建/追加课时账户 → 写入账流水` 三步在同一事务。
3. **支付回调幂等**：订单号全局唯一，回调按订单号 `SELECT ... FOR UPDATE` 加锁，已支付直接返回成功（防微信/支付宝重复回调）。✅ 已实现（`StudentOrderServiceImpl.markPaid` 行锁读取订单）。
4. 一学员一课包只能有**一张未完成订单**（应用层校验 + 数据库唯一索引 `UK_ORDER_UNPAID` 兜底防重复下单）。✅ 已实现（生成列 `UNPAID_FLAG` + 唯一索引）。

### 2.3 消课流程（点名联动，核心中的核心）

触发：老师对某次排课点名，学员状态为 `到课 / 请假 / 缺勤`。

| 点名状态 | 默认扣课 | 说明 |
|---|---|---|
| 到课 | 扣 1 课时 | 每课扣课时数可在**课程**上配置（`COURSE.LESSONS_PER_CLASS`，如 1.5 课时/次） |
| 请假 | 不扣 | 可配置「请假是否扣课」（`COURSE.LEAVE_DEDUCT`，默认不扣） |
| 缺勤 | 扣 1 课时 | 可配置「缺勤是否扣课」（`COURSE.ABSENT_DEDUCT`，默认扣） |

> 扣课规则落在课程维度（排课点名时按班级取课程配置），如需按课包差异化可在课务扩展中补充。✅ 已实现（课程管理页可配置）。

事务边界（**同一事务**，缺一不可）：

```
1. 行锁课时账户  SELECT ... FOR UPDATE   （防同一学员并发点名/并发续费）
2. 校验 REMAIN_LESSONS >= 本次扣课时数    （不足 → 业务异常"课时不足，请先续费"，点名不落库）
3. 扣减账户余额
4. 写课时流水（类型=点名消课，记录 排课id、点名状态、操作人）
```

防重复扣课：`COURSE_CLASS_ATTEND` 上 `(SCHEDULE_ID, STUDENT_ID)` **唯一索引**；同一学员对同一排课只能有一条点名记录。

### 2.4 撤销点名（回补）

- 场景：点错 / 学员实际未到。
- 动作：删除点名记录（或置状态`已撤销`）→ 反向回补账户余额 → 写一条类型=`回补`、`关联流水=原消课流水id` 的流水（负数入账）。
- 权限：仅教务/校长可撤销，记录操作人（审计要求）。

### 2.5 退费流程（STUDENT_REFUND）

状态机：

```
待审批 ──通过──▶ 待退款 ──退款完成──▶ 已退款
   │                  │
   └──驳回──▶ 已驳回  └──（线下退款则直接完成）
```

规则：

1. 可退课时 = `剩余课时 - 赠课课时`（**赠课不退**，需在账户上分别记录 `TOTAL_LESSONS` 与 `GIFT_LESSONS`）。
2. 折算单价 = `实付金额 / (课包课时) `（赠课不计入分母）。
3. 通过审批后：账户置`冻结` → 退款完成后账户`清零`并写退费销课流水。
4. 同一订单只允许一张在途退费单（唯一约束：`(ORDER_ID, 状态 in 待审批/待退款)`）。

### 2.6 续费预警（定时任务）

- 扫描频率：每日一次（DEV_JOB，hutool-cron）。
- 触发条件（机构可配置，默认值）：`剩余课时 ≤ 3`，或课包有效期 `7 天内到期`。
- 产出：写入 `STUDENT_RENEW_WARN`（学员、课程、剩余课时、触发原因、状态`待处理/已续费/已忽略`）。
- **去重**：同一学员×课程 7 天内不重复生成（按学员课程维度查最近一条预警时间）。
- 通知：机构端待办 + 家长端订阅消息（异步，失败不阻塞主流程）。
- 续费动作：新订单支付成功 → 把该学员课程的预警置为`已续费`。

### 2.7 人工调整

- 场景：赠送课时、扣错补正、前台"先上课后补费"。
- 统一走 `人工调整`（ADJUST）流水类型，必填 `调整原因` + 操作人，其余走正向/负向流水，余额不允许为负（负向调整超余额时拦截）。
- ✅ 已实现：`POST /student/lessonAccount/adjust`（学员详情页 → 课时账户 → 调整课时）。
  - 正数（赠送/补录）：总课时与剩余课时同时增加；
  - 负数（收回）：总课时与剩余课时同时减少，剩余不足直接拒绝；
  - 流水记录原因与操作人（`StpUtil.getLoginIdAsString()`），不影响 `USED_LESSONS`。

## 三、排课细则

### 3.1 排课生成（COURSE_SCHEDULE）

- 班级持有"周课表模板"（星期 + 开始时间 + 时长 + 教室 + 教师）。
- 按模板**批量生成 N 周**排课（默认 4 周，可配）。
- **冲突检测**（生成时校验，任一冲突即拒绝生成）：
  1. 同教室 + 同时段（含跨排课重叠）冲突；
  2. 同教师 + 同时段冲突；
  3. 同班级 + 同时段冲突。
- 冲突检测基于已生成的排课表做区间重叠判断（应用层实现，SQL 查重叠区间即可）。

### 3.2 排课状态机与调课

```
正常 ──调课──▶ 已调（新排课取代）  正常/已调 ──取消──▶ 已取消
```

调课流程（单事务）：

```
1. 原排课置"已调"（保留历史，供流水/报表追溯）
2. 生成新排课（新时间/教师/教室，做冲突检测）
3. 写 COURSE_SCHEDULE_CHANGE（原因、操作人、新旧时间）
4. 通知该班所有在学学员家长（订阅消息，异步）
```

规则：点名基于**最新有效排课**；已产生点名流水的排课仍可调课，但新点名以新排课为准；取消排课不影响历史流水。

### 3.3 点名与课表联动

- 教师端按班级/日期看到课表 → 点名 → 走 §2.3 消课事务。
- 一次点名页面 = 遍历该排课的在学学员（`COURSE_CLASS_STUDENT`），逐学员生成点名记录并扣课；**任一学员余额不足**：整单回滚（同一事务），提示"第 N 名学员课时不足"，教师可先跳过该学员点名（跳过 = 不生成点名记录，视为未点名，可后续补点）。
- 补点名：未点名学员可单独补点名（幂等由唯一索引保证）。

## 四、Service 接口设计（含事务边界）

> 命名/返回值风格与底座一致（`CommonResult`、`Page`、Param 对象），事务用 `@Transactional(rollbackFor = Exception.class)`。

### 4.1 `StudentLessonService`（课时账务）

```java
/** 创建订单（课包快照、幂等防重复下单） */
CommonResult<String> signUp(StudentOrderAddParam param);

/** 支付成功回调（幂等：行锁订单） */
void payCallback(String orderId, String channel, String tradeNo);

/** 点名并扣课（单事务：锁账户→校验→扣减→流水） */
void attend(List<ScheduleAttendParam> attendList);

/** 撤销点名并回补课时（单事务） */
void cancelAttend(ScheduleAttendParam param);

/** 提交退费申请 */
void applyRefund(StudentRefundAddParam param);

/** 审批退费（通过→冻结账户；驳回→解冻） */
void approveRefund(String refundId, Boolean pass, String opinion);

/** 确认退款完成（账户清零 + 退费销课流水） */
void confirmRefund(String refundId);

/** 人工调整课时（正负流水 + 原因） */
void adjustLessons(StudentLessonAdjustParam param);

/** 续费预警扫描（定时任务调用） */
void renewWarnScan();
```

### 4.2 `CourseScheduleService`（排课）

```java
/** 按周模板批量生成排课（含冲突检测，任一冲突整体失败） */
CommonResult<List<CourseSchedule>> generateBatch(CourseScheduleGenerateParam param);

/** 调课（原排课置已调 + 新排课 + 变更记录 + 通知） */
void change(CourseScheduleChangeParam param);

/** 取消排课（无点名流水才允许，否则提示先处理点名） */
void cancel(CourseScheduleIdParam param);

/** 冲突检测（返回冲突明细，供前端即时校验） */
CommonResult<List<ConflictInfo>> conflictCheck(CourseScheduleGenerateParam param);
```

### 4.3 事务与锁的边界约定

| 场景 | 手段 |
|---|---|
| 支付回调重复 | 订单行锁 + 状态判断 |
| 并发点名同一学员 | 账户行锁（FOR UPDATE）+ 点名唯一索引 |
| 并发续费 + 点名 | 同一把账户锁，先到先得 |
| 整批点名部分失败 | 单事务整体回滚 |
| 异步通知失败 | 不参与业务事务，重试队列（M5 前用简单重试即可） |

## 六、异常场景与规则清单（开发与测试用例依据）

1. 余额不足点名 → 事务回滚，整批不落库，提示"课时不足，请先续费"。
2. 重复点名（同排课同学员）→ 唯一索引拦截，返回"已点名"。
3. 重复支付回调 → 幂等返回成功，不重复入账。
4. 退费中（账户冻结）→ 不允许点名扣课。
5. 已退费/已清零账户 → 不允许再扣课。
6. 撤销点名时原流水已不存在（数据异常）→ 抛业务异常，人工介入。
7. 调课目标时段冲突 → 拒绝并返回冲突明细。
8. 取消有流水排课 → 拒绝（提示先处理点名）。
9. 并发：教师点名 与 前台续费 同时发生 → 行锁串行，数据最终一致。
10. 课时/金额精度：一律 BigDecimal，禁止 double/float。
11. 人工调整超出剩余课时 → 直接拒绝（"剩余课时不足"），不做负余额。
12. 同一学员同课包重复下单 → 应用层提示；并发穿透由唯一索引 `UK_ORDER_UNPAID` 兜底（异常转换为业务提示）。

## 七、开发顺序建议（核心域内）

1. 数据表 + 实体 + 通用流水服务（Flow 先于 Account 扣减）。
2. 订单/支付回调（幂等）→ 账户入账。
3. 排课生成 + 冲突检测 → 点名 → 扣课。
4. 撤销/回补 → 退费。
5. 续费预警定时任务 + 通知。
每步都可用 gen 生成 CRUD 骨架后替换 Service 实现，前端页面用 admin-web 现有组件。
