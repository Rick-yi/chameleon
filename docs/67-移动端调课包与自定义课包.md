# 移动端调课包与自定义课包

## 一、需求与方案选择

需求：移动端进入学员详情后可以「调课包」，甚至「自定义课包」。

调研现状：

- 移动端学员详情已有「报名 / 续费」，走 `EnrollmentFlow`，只能从预设课包里选；
- 后端 `StudentOrderAddParam` 只有 `coursePackageId`，下单必须命中 `COURSE_PACKAGE` 表；
- 没有任何「换课包 / 升级 / 补差价」概念。

「调课包」有三种可选做法，账务影响差别很大：

| 做法 | 影响 |
| --- | --- |
| 新增订单追加课时 | 历史可追溯、退费仍按各自订单核算，风险最低 |
| 直接改现有课包/账户 | 不产生订单，审计追溯弱，已收款金额被改后对账困难 |
| 换课包（退旧买新） | 需折算剩余课时、资金冲正，改动最大 |

采用第一种：**每次调整生成一笔新订单，课时叠加到账户**。理由与项目既定的账务原则一致——一手证据（订单）、可追溯、退费按订单核算不受影响。

## 二、关键发现：下游链路不用改

`StudentLessonAccountServiceImpl.recharge(order)` 的入账依据是订单快照：

```java
BigDecimal totalAdded = order.getPackageLessons().add(order.getPackageGiftLessons());
```

退费试算同样读订单快照（`packageLessons` 与 `paidAmount`）。因此只要下单时把自定义课时/价格写进订单，**账户累加、退费核算、财务报表全都不需要改**。

## 三、后端改动

### 下单支持自定义课包

`StudentOrderAddParam` 新增可选字段：`courseId`、`packageName`、`packageLessons`、`packageGiftLessons`、`packageValidityDays`、`amount`、`remark`。

`StudentOrderServiceImpl.add` 按 `coursePackageId` 是否为空分支：

- **预设课包**：原逻辑不变（查课包快照 + 同课包待支付去重）；
- **自定义课包**（新增 `fillCustomPackage`）：
  - 必须选课程、填正数课时与非负金额；
  - 课包名称留空时默认「自定义课包（课程名）」；
  - 防重复提交：同学员同课程已有待支付的自定义订单则拒绝；
  - 不写入 `coursePackageId`（NULL），不受 `UK_ORDER_UNPAID` 约束影响。

### 修掉一个链路断点

首次验证时收款直接失败：

```
收款: 500 课包不存在，id值为：null
```

根因在 `recharge`：它靠 `courseApi.getCoursePackageInfo(order.getCoursePackageId())` 反查课程 id，自定义订单没有课包记录，必然拿不到。

改为**优先取订单快照里的 `courseId`**，仅当为空时才回退查课包。同时把 `getPackageGiftLessons()` 统一走 `nvl`，避免历史数据空值 NPE。

## 四、移动端改动

学员详情抽屉里，「报名 / 续费」下方新增「调课包」按钮（同样按 `/student/order/add` 权限控制显隐）。

点开是一张移动端表单：

- 课程（必填，搜索选择）
- 方式：**预设课包 / 自定义** 分段切换
- 预设：按所选课程过滤课包列表
- 自定义：课时、赠课、有效期（天）、应收金额
- 立即收款开关 + 渠道
- 底部实时显示「本次应收」，与下单金额一致

提交后：下单 → 若开启立即收款则接着走线下收款 → 刷新列表与课时账户。收款失败时保留订单并提示去收款台补收（与 PC 报名行为一致）。

## 六、说明与未做

- **不做「换课包（退旧买新）」**：那需要剩余课时折算与资金冲正，属独立议题，本轮不含。
- 自定义课包不写入 `COURSE_PACKAGE` 表，只存在于订单快照；因此它不会出现在课包管理列表里，这是有意为之——避免把一次性价格变成可复用商品。
- 未发布生产。
