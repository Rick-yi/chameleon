# 安全、性能与账务口径加固

本轮针对代码通读发现的问题做修复，重点是生产暴露面、热路径查询次数、账务算式一致性，以及让"忘记登记租户表"这类隐性风险在启动时自己暴露出来。

## 一、生产 Druid 监控台暴露（安全问题）

### 问题

三处配置叠加构成了实际暴露：

- `application.properties` 里 `stat-view-servlet.enabled=true`，且账号是 `admin / 123456`；
- `application-prod.yml` 完全没有提及 druid，生产完整继承了上面的默认值；
- `GlobalConfigure.NO_LOGIN_PATH_ARR` 里包含 `/druid/**`，平台自身的登录校验对它直接放行，只剩 Druid 自带表单登录；
- `nginx` 的 `location /api/` 会把 `/api/druid/**` 原样转发到后端。

公网访问 `/api/druid/index.html` 即可看到连接池状态、慢 SQL、执行次数与表结构。

### 修复

| 位置 | 改动 |
| --- | --- |
| `application.properties` | 默认 `enabled=${DRUID_STAT_ENABLED:false}`，账号口令改为环境变量，默认口令置空 |
| `application-prod.yml` | 显式 `stat-view-servlet.enabled: false`，不接受环境变量覆盖 |
| `GlobalConfigure` | 从 `NO_LOGIN_PATH_ARR` 移除 `/druid/**`，即使开启也必须先通过平台登录 |
| `nginx.conf.template` / `nginx.bare.conf` | 新增 `location /api/druid/ { deny all; return 404; }` |

三层防护：默认关闭 → 生产强制关闭 → 网关拒绝。监控台仅在本地排查性能问题时通过 `DRUID_STAT_ENABLED=true` 临时打开，且仍需登录态。

### 验证

- `curl /druid/index.html` 返回平台 `401 未能读取到有效 token`，响应体不含任何 Druid 页面特征。

## 二、课表热路径的 N+1 查询

课表周视图是每天都会打开的页面，里面有两处逐条查库。

### 班级在读人数

原实现对每个 `classId` 单独调用 `listByClassId`，而附近 20 行前已经用 `selectBatchIds` 批量取过班级。一周 20 个班 = 20 次查询。

新增 `CourseClassStudentService.countStudyingByClassIds`：一次 `IN` 查询 + 内存 `merge` 计数，替换整个循环。

### 教师下拉

`teacherOptions` 对 `listUserOptions` 返回的每个用户（上限 200）调用一次 `ownRoleCode`，而该方法内部先查角色 id 再 `listByIds` 查角色，等于 2N 次查询，且前端每次进课表页都会触发。

新增 `SysUserApi.ownRoleCodeMap(List<String>)`：一次查全部「用户-角色」关系，再一次查涉及的全部角色，固定 2 次查询。

### 验证

| 接口 | 结果 |
| --- | --- |
| `/course/schedule/teacherOptions` | 200，2 条选项，105ms |
| `/course/schedule/week` | 200，138ms |

## 三、退费金额口径统一

### 问题

"实付 ÷ 课包课时保留 4 位 → 可退课时 × 单价保留 2 位"这套算式在 `StudentRefundServiceImpl` 里写了三遍：申请（194-201）、试算（219-220）、审批（270-273）。三段当时算出来一致，但这种一致性完全靠人工同步维持，哪天改口径漏掉一处，同一订单就会出现三个不同金额。

### 修复

新增 `RefundAmountCalculator`，算式只在这里实现一次：

- `unitPrice(paidAmount, packageLessons)`：保留 4 位，`HALF_UP`
- `refundAmount(refundLessons, paidAmount, packageLessons)`：保留 2 位，`HALF_UP`
- `calc(...)`：一次返回单价与金额

三个调用点全部改为调用该类，删除了本地重复算式与 `RoundingMode` 引用。

### 测试

`RefundAmountCalculatorTest`（10 个用例）除了逐条验算，重点是不变量：

- 试算、申请、审批三处对同一输入必须得到同一金额；
- 退费金额不超过实付金额；
- 可退课时为 0 时金额为 0；
- 金额随可退课时单调不减；
- 课包课时为 0 或空时拒绝计算，不静默返回 0。

## 四、租户隔离自检

### 背景

行级隔离依赖 `GlobalConfigure.TENANT_TABLES` 这个手工白名单：登记过的表由拦截器自动拼 `TENANT_ID`，未登记的表完全靠服务层手写条件。这个模式的问题是——漏写的查询不会报错，只会在某天被人发现查到了别家机构的数据。

### 修复

1. **补齐登记**：把 5 张此前靠手写过滤的新表纳入白名单——`STUDENT_TAG`、`STUDENT_TAG_REL`、`STUDENT_STATUS_LOG`、`STUDENT_RENEW_WARN_CONFIG`、`STUDENT_FOLLOW_RECORD`。
2. **新增 `TenantIsolationAudit`**：启动时比对数据库里「真正含 `TENANT_ID` 列」的表与白名单，对未登记的表输出告警清单。这是提醒而非拦截，避免存量表改造期间阻塞发布。
3. **平台表豁免**：`T_TENANT*`、`T_PLATFORM_*`、`DEV_JOB` 归平台侧，不参与租户隔离。其中 `DEV_JOB` 的 `TENANT_ID` 只标记任务归属，调度器在无租户上下文时要扫描全部租户任务，纳入拦截器反而会被拼成 `TENANT_ID='0'` 而漏任务。
4. **修正一处语义变化**：配置表登记后 `getById` 会带上租户条件，跨租户 id 返回空。原代码此时会静默走新建流程，改为显式报「不存在或无权修改」。

### 验证

- 首次启动即抓到 `DEV_JOB` 未豁免（说明自检有效），加入豁免后重启输出：`租户隔离自检通过：含 TENANT_ID 的 50 张业务表均已登记`。

## 五、测试与 CI

- 新增 `RefundAmountCalculatorTest`（10 个）、`StudentStatusMachineTest`（10 个），后端测试从 32 个增至 52 个，全部通过。
- 学员状态机规则从服务层抽到 `StudentStatusMachineEnum`（`resolveTarget` / `reasonRequired` / `normalizeReason`），服务层只负责取数与落库，测试直接覆盖生产逻辑。
- `package.json` 增加 `lint` / `lint:fix` 脚本，CI 增加代码规范检查步骤。

### 关于 lint 的取舍

本轮初版曾把 lint 设为 `continue-on-error: true`：存量 663 个前端文件中有 105 个存在格式问题（1557 条），`eslint --fix` 会重排近百个文件，会产生与功能修复完全无关的巨大 diff 并掩盖真实改动。

随后已单独完成存量格式化（见 `docs/59`），因此 CI 的代码规范检查**已去除 `continue-on-error`，lint 现在是阻断关卡**。
