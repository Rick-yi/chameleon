# 核心业务流程补测

前几轮补的测试都集中在**抽出来的纯函数**上，`StudentRenewWarnServiceImpl`（839 行）与 `StudentRefundServiceImpl`（433 行）的编排逻辑仍无覆盖。本轮把其中「改错了不报错、只让业务静默出错」的判定规则抽出来补测。

## 一、为什么不建集成测试基座

仓库里没有 H2/Testcontainers，只有 `spring-boot-starter-test`。引入 H2 的代价不小：本项目大量使用 MySQL 特有语法（`JSON_ARRAY_APPEND`、`JSON_SET`、`INSERT IGNORE`、`ON DUPLICATE KEY`），H2 兼容模式跑不通这些迁移 SQL；Testcontainers 则需要 Docker，CI 里要额外等待镜像拉取。

因此采用「抽纯函数 + 单测」的方式：把判定规则从流程代码里剥出来，让它们不依赖数据库即可覆盖。这不能替代集成测试，但能守住最容易出错、且出错后最难发现的部分。

## 二、续费预警判定规则

### 抽出的规则

`scan()` 里原本混着三段判定，抽成 `RenewWarnRules`：

| 方法 | 职责 |
| --- | --- |
| `resolveWarnReason` | 判定该不该预警、报什么原因 |
| `shouldCreateWarn` | 重复间隔去重 |
| `isBeyondRepeatInterval` / `isExpired` | 间隔与过期辅助判定 |

### 规则要点

- **课时不足优先于即将到期**。两者同时满足时报课时不足——这是更需要立即跟进的信号。
- **已过期不再报「即将到期」**。已过期属于流失场景，若继续标记为待续费，销售会把流失学员当成待续费客户去骚扰。
- **待处理预警不重复生成**，已处理/已忽略/已续费在间隔天数内不重复提醒。

### 测试覆盖（22 个）

重点是不变量与边界：

- 剩余课时**等于**阈值也要预警（含等号）
- 课时不足 + 临近到期同时成立时，报课时不足
- 已过期账户不报「即将到期」
- 到期日超出提前天数不预警
- 阈值调大后原本充足的课时会触发（阈值与触发概率正相关）
- 课时从阈值向下递减时始终触发（单调性）
- 待处理状态下即使间隔很久也不重复生成
- 已处理状态超过间隔后允许再次生成
- `repeatDays = 0` 时同一天允许再次生成
- 有状态但无时间时按可生成处理，避免永久卡住

**用的是枚举常量而非字符串字面量**，避免以后改枚举值时测试与生产代码一起漂移却互不报错。

## 三、退费账户状态判定

### 抽出的规则

`confirm()` 与 `cancel()` 各有一份完全相同的判定：

```java
remainLessons.compareTo(BigDecimal.ZERO) > 0 ? NORMAL : CLEARED
```

抽成 `RefundAccountStatusResolver.resolve()`，两处共用。

### 判定错了会怎样

- 错误地判成 CLEARED：学员剩余课时在但账户被清零，无法继续上课；
- 错误地判成 NORMAL：课时已用完却还能排课，后续点名扣课会扣成负数。

都是账务级故障，且不会抛异常。

### 顺带补的前置校验

`canDeduct()` 校验余额是否足够扣减。数据库层原本有 `ge` 约束兜底，但 SQL 条件不满足时只返回「课时账户数据异常，退费失败」，排查时不知道是哪个余额不够。现在提前给出「课时账户余额不足，无法完成退费」。

### 测试覆盖（12 个）

- 剩余为正 → NORMAL；为 0 → CLEARED
- **不同精度的 0 都判为 CLEARED**：`BigDecimal("0.00").equals(BigDecimal.ZERO)` 返回 false，业务上必须用 `compareTo`
- null 剩余视为 CLEARED，不空指针
- 余额**刚好相等**时允许扣减（含等号边界）
- 剩余课时不足、赠课余额不足分别拒绝
- 扣减课时为 0 或负数拒绝
- 余额为 null 视为 0

## 四、端到端验证

除了单测，还用真实数据跑了一遍完整退费流程：

```
1) 试算    可退课时=20  金额=3600  单价=180
2) 申请    code=200
3) 待审批  状态=PENDING 金额=3600
4) 审批    code=200
5) 确认    code=200
```

退费前后账户变化：

| 项 | 退费前 | 退费后 |
| --- | --- | --- |
| 总课时 | 264 | 242 |
| 剩余课时 | 262 | 240 |
| 赠课 | 24 | 22 |
| 状态 | NORMAL | **NORMAL**（剩余 240 > 0，判定正确） |

销课流水 `REFUND / -20.00` 正确。订单状态转为 `REFUNDED`。

验证完成后已把演示数据完整还原（账户课时、订单状态、删除测试退费单与流水），环境无残留。

## 六、仍未覆盖的部分

抽纯函数只能测「规则」，测不到「编排」：

- `scan()` 的事务边界、通知落库失败是否影响主流程；
- 退费 `approve` 里冻结账户的乐观锁（`frozen == 0` 时抛异常）；
- `confirm` 里先扣减再改状态的原子性；
- 跨表一致性（退费单、账户、流水、订单四者是否总是同步）。

这些需要能连真实数据库的集成测试，建议后续单独引入 Testcontainers 并优先覆盖退费与点名扣课这类资金相关路径。本轮未做，是为了避免在 CI 里引入 Docker 依赖影响现有流水线的稳定性。
