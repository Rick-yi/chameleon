# 启动可靠性与前端安全加固

本轮处理代码通读中剩下的四项：租户取值的重复实现、启动迁移失败被静默吞掉、`v-html` 渲染用户可写内容、以及续费预警核心规则缺测试。

## 一、租户取值收敛到一处

`RenewWarnTenantUtil` 与 `StudentTagServiceImpl` 各有一份完全相同的实现：

```java
StrUtil.blankToDefault(TenantContext.getTenantId(), "0")
```

兜底值 `"0"` 在两处各写一遍，以后要改（比如区分平台租户）必然漏改一处。

**修复**：把 `currentTenantId()` 和 `DEFAULT_TENANT_ID` 放回 `TenantContext` 本身——它是租户上下文的唯一持有者，兜底值本就该由它定义。两处旧实现改为委托并标记 `@Deprecated`，存量调用点无需改动。

## 二、启动迁移失败不再静默

### 问题

12 个迁移监听器的失败处理一模一样：

```java
} catch (Exception e) {
    log.error(">>> xx升级失败，请手工执行 xxx.sql", e);
}
```

应用照常启动、照常对外服务，但表结构或权限没升级。故障会推迟到业务调用时才暴露，且堆栈指向业务代码而不是根因。更麻烦的是失败日志散落在 12 个类里，运维要翻遍日志才知道哪一项没跑成功。

### 修复

新增 `StartupMigrationRegistry`（`snowy-common`）：迁移失败时调用 `record(名称, 原因)` 集中登记。`TenantIsolationAudit` 在最后统一输出汇总：

- 全部成功：`>>> 启动期结构/权限迁移全部成功`
- 有失败：`ERROR` 级别列出每一项的名称与原因，并提示「应用已启动但这些变更未生效」

同时把 `isEnabled` 改为静态，供新抽出的优先级方法复用。

### 验证

本地启动确认成功路径输出正确。失败路径通过单元测试覆盖（7 个用例）：登记、多失败保序、同名覆盖、空原因兜底、返回副本不可污染内部状态、清空重置。

尝试用「删表 / 建不完整表」制造真实失败未成功——因为迁移本身是幂等的，会自动重建表和补列。这反而是个好消息，说明迁移比预期健壮。

## 三、`v-html` 渲染用户可写内容（存储型 XSS 面）

### 排查结果

4 处 `v-html`，性质不同：

| 位置 | 内容来源 | 结论 |
| --- | --- | --- |
| `views/biz/notice/detail.vue` | 公告正文，编辑器写入 | **需净化** |
| `components/HomeCard/BizNoticeCard/detail.vue` | 同上，首页卡片入口 | **需净化** |
| `dev/config/emailTemplateConfig/preview.vue` | 管理员正在编辑的模板 | 不净化，见下 |
| `layout/menu/topMenu.vue` | eslint 误报，实际无 v-html | 无需处理 |

公告的风险是真实的：正文由编辑器产生并存库，任何有权查看公告的人打开页面都会执行其中的脚本——包括权限更高的人。当前只有 `superAdmin` 有公告编辑权限（查库确认），所以是「内部管理员互信」级别，但一旦将来把公告权限下放给运营或分校角色，就会变成可利用漏洞。

### 修复

新增 `src/utils/sanitize.js`，基于 `dompurify`（原为 mermaid 的传递依赖，已提升为直接依赖）：

- 禁止 `iframe` / `form` / `input` / `button` / `style` / `link` / `meta` / `base`
- 外链统一补 `rel="noopener noreferrer"`
- 保留常规排版标签与样式

两个公告详情页改为 `computed(() => sanitizeHtml(content))` 后再交给 `v-html`。

### 邮件模板预览为何不净化

内容是当前管理员**正在编辑**的模板本身，输入者与查看者是同一人，不存在「他人写入、我执行」的链路；而净化会改变实际渲染效果，让预览与真实发信结果不一致。已在代码与 eslint 配置里注明：若将来改为预览他人共享的模板，必须改为 `sanitizeHtml`。

### 净化效果实测

在真实浏览器（CDP 驱动）里加载 DOMPurify 逐个验证：

| 输入 | 输出 | 结论 |
| --- | --- | --- |
| `<p>ok</p><script>alert(1)</script>` | `<p>ok</p>` | 脚本被移除 |
| `<img src=x onerror="alert(1)">` | `<img src="x">` | 事件属性被剥离 |
| `<a href="javascript:alert(1)">x</a>` | `<a>x</a>` | 协议被清空 |
| `<a href="https://example.com">link</a>` | 原样保留 | 正常外链不受影响 |
| `<h2>T</h2><p>p<strong>b</strong></p>` | 原样保留 | 排版完整 |
| `<p style="color:red">红字</p>` | 原样保留 | 行内样式保留 |

## 四、续费预警配置优先级

「班级 > 课程 > 默认」是续费预警的核心口径：顺序或启用判断被改错时不会报错，只会让整个机构的预警阈值静默失效——所有人要么集体不预警，要么集体误报。

原实现埋在一段 `resolve()` 里，依赖 `devConfigApi` 无法单测。抽出静态方法 `pickByPriority(studentId, courseId, configList, classConfigMap)`，`resolve()` 只负责取系统兜底值。

`RenewWarnConfigPriorityTest`（10 个用例）覆盖：班级优先于课程与默认、课程优先于默认、课程只对匹配课程生效、仅默认时回落、停用的班级/课程配置被跳过、全部停用返回 null、空列表返回 null、班级配置只对映射的学员生效、`enabled` 为空视为启用。

## 六、未做与说明

- **迁移排序仍靠数字间距**（`LOWEST_PRECEDENCE - 20/-15/-14/-13/-10`）。本轮只解决了「失败静默」，没有重构排序机制。改成显式的阶段常量会更清晰，但涉及全部 12 个迁移的联动改动，风险与收益不匹配，建议单独一轮。
- **`v-html` 仍有 3 条 eslint warning**：已确认都是上述已处理或已论证的场景，在 `.eslintrc.js` 里按文件豁免并注明原因，未全局关闭规则。
- 剩余 13 条 warning 为模板变量遮蔽（`day`、`record`、`module`），不影响运行。
