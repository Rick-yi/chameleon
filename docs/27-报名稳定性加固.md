# 27 · 报名稳定性加固（第一批）

> 对应问题清单里的 P0「成功提示但未落库」与 P1「登录被踢、重复建档」。
> 这一批不改页面主流程，重点是把“成功”变成可信的、把重复提交挡在服务端。

---

## 一、成功判定：不再只看前端提示

- 后端在 `quickEnroll` 成功后输出结构化日志：
  `tenantId / requestId / studentId / orderId`，便于用 traceId 对照接口返回与数据库记录。
- 前端只有拿到 `studentId` 才展示“报名成功”；响应缺少学员编号时提示失败并停留在当前页，避免出现“提示成功但库里没有”。
- 失败时保留表单内容，不回滚用户已填信息。

## 二、重复提交：前端防抖 + 服务端幂等

报名接口新增 `requestId`（前端每次提交生成 UUID）：

1. 同一租户 + 同一 `requestId` 在 Redis 中只允许一个请求进入处理；
2. 处理中的重复请求返回「报名正在处理中，请勿重复提交」；
3. 已成功的重复请求直接返回上次的 `studentId/orderId`，不会建第二条学员；
4. 事务提交后才缓存结果，回滚会释放幂等键，允许修正后重试；
5. 结果缓存 10 分钟，处理中的占位 60 秒。

前端同时增加提交锁：`submitting` 未结束时按钮禁用，连续点击只会发一次请求。

## 三、重复建档提醒

- 家长手机失焦时按手机号精确查询已有学员；
- 命中后显示「该手机号已有学员：张三」，提供「查看」入口直接打开详情；
- 只提示不阻断：同一手机号可能是兄弟姐妹，是否新建由前台决定。

## 四、登录会话与恢复

- 会话策略改为允许多端同时在线：`is-concurrent=true`、`max-login-count=3`，避免 PC 和手机互相踢下线。
- 登录失效后不再简单刷新页面：
  - 当前路径写入 `redirect`，重新登录后回到原页面；
  - 未登录直接访问业务路由时也保留 `redirect`；
  - 报名弹窗把表单草稿写入 `sessionStorage`，重新打开时恢复并提示「已恢复上次未提交的报名内容」，提交成功或主动取消后清除。

## 五、验证记录

| 场景 | 结果 |
|---|---|
| 并发两次相同 `requestId` | 一次成功，另一次返回「报名正在处理中」；数据库仅 1 条学员 |
| 成功后再用相同 `requestId` 重试 | 返回同一 `studentId`，不新增记录 |
| 手机号命中已有学员 | 表单出现「该手机号已有学员：张小明 查看」 |
| 填写后刷新页面再打开弹窗 | 恢复姓名/手机号并提示草稿已恢复 |
| 令牌被服务端删除后点击查询 | 弹「登录已失效」→ 重新登录 → 回到原页面 |
| 未登录直接访问 `/student` | 跳转 `/login?redirect=/student`，登录后回到学员页 |
| 三步报名完整回归 | 订单 `PAID`、实收 3600、成功页正常，日志含 `studentId/orderId` |

## 六、后续

- 第二批：工作台与学员详情共用同一套报名流程，去掉重复表单代码；
- 折扣超过阈值时要求填写原因，并在订单上记录优惠金额；
- 学员批量导入与手机端全量回归。
