# 账务不变量校验

## 一、为什么没做集成测试基座

上一轮遗留的问题是「编排逻辑未被测试覆盖」，我原计划引入 Testcontainers 覆盖退费与点名两条资金路径。开工前先确认环境：

```
docker --version  →  command not found
```

本机没有 Docker，Testcontainers 跑不起来。而 H2 也不可行——迁移 SQL 大量使用 MySQL 特有语法（`JSON_ARRAY_APPEND`、`JSON_SET`、`INSERT IGNORE`、`ON DUPLICATE KEY UPDATE`），H2 兼容模式无法执行。

于是改变策略：**先审查资金路径本身，再补能补的测试**。

## 二、资金路径审查结果

逐一核对了四处并发与一致性保护，结论是**都完整**：

| 位置 | 保护方式 | 结论 |
| --- | --- | --- |
| 点名扣课 | 条件更新 `eq(状态=NORMAL).ge(剩余, 扣减量)`，`!deducted` 即抛异常 | 完整 |
| 点名幂等 | 已存在出勤记录直接 `continue`，不重复扣课 | 完整 |
| 退费审批冻结 | `frozen == 0` 抛「账户状态已变化」 | 完整 |
| 退费确认扣减 | `ge(剩余, totalRemove).ge(赠课, gift)`，`accountUpdated == 0` 抛异常 | 完整 |
| 退费单状态流转 | 每次 `update` 都校验 `updated`，失败抛异常 | 完整 |

没有发现可利用的并发缺陷。

## 三、发现的问题：账务不变量无人校验

审查中注意到账户表维护三个互相约束的字段：

```
剩余课时 = 总课时 - 已用课时
```

这个不变量由**四条独立的 SQL** 分别维护：

- 点名扣课：`USED + x`、`REMAIN - x`
- 课时回补：`USED - x`、`REMAIN + x`
- 报名加课：`TOTAL + x`、`REMAIN + x`
- 退费扣减：`TOTAL - x`、`REMAIN - x`

任何一处漏改或写错，**都不会立即报错**，只会在某次退费试算或财务报表里算错金额，而且要追溯到很久之前才能定位。

系统里没有任何自检机制。

### 新增校验器

`LessonAccountInvariant`（`studentlessonaccount/util`）：

- `check(total, used, remain)` → 返回自洽性、推算值、实际值、偏差
- `isNegativeRemain` / `isOverused` → 两个明确的异常信号
- 偏差带方向：`overCredited()`（少扣了课）、`underCredited()`（多扣了课）

**用 `compareTo` 而非 `equals`**：`BigDecimal("263.00").equals(new BigDecimal("263"))` 为 false，用 equals 会把自洽的账户误判成漂移。

### 接入位置

接在退费确认路径上——那里本来就要重新读账户，零额外查询。漂移**只告警不阻断**：资金操作不能因为一次自检失败就卡住用户，但必须留下明确日志。

### 顺带发现的真实数据问题

本地演示数据 `la_ux_001` 实测：

```
TOTAL=264  USED=1  REMAIN=262  →  推算 263，偏差 1
```

这不是代码 bug，是历史演示数据（我上一轮做端到端验证后手工还原时未精确对齐 `USED`）。已经用一次真实退费验证了校验器在正常流程下**不误报**（退费后 242 - 1 = 241，完全自洽，无告警），随后把演示数据对齐回自洽状态。

## 四、测试覆盖（9 个）

- 三项自洽时通过
- **精度不同但数值相等仍判定自洽**（守住 `compareTo` 这个坑）
- 少扣课导致剩余虚高 → 偏差为正
- 多扣课导致剩余偏低 → 偏差为负
- 空值按 0 处理，不空指针
- 剩余为负、已用超总量分别被识别
- 跨业务序列：报名 30 → 扣 3 次 → 回补 1 次 → 退费扣 10 总量，每步都校验不变量
- 退费只扣总量不扣已用，剩余相应减少后仍自洽

## 六、仍未覆盖的部分

审查确认并发保护是完整的，但「完整」是读代码得出的结论，**没有被自动化测试守住**。真正的风险是以后有人改动这些条件更新时把保护去掉。

需要真数据库才能覆盖的点：

- 条件更新在并发下的实际行为（两个请求同时扣同一账户）
- 事务回滚边界（扣课成功但流水写入失败时是否整体回滚）
- 四表一致性（退费单、账户、流水、订单）

建议后续在有 Docker 的环境中引入 Testcontainers，只覆盖退费与点名两条路径。本轮在无 Docker 环境下强推会得到一个跑不起来的测试，反而降低 CI 可信度，故未做。
