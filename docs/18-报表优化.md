# 18 · 报表优化：数据及时性、口径与环比

> 报表这轮不改版式，只解决三件影响判断的事：收完钱报表还是旧数、漏斗可能倒挂、KPI 没有参照。

---

## 一、报表缓存随业务写入自动失效

### 问题

财务报表（汇总、趋势、看板、收款明细、退费明细、消课）按「租户 + 参数」缓存，过期时间原来 5 分钟。
缓存只在手动「重算当日汇总」或调用清理接口时才清——前台刚收完一笔款，财务看板最多 5 分钟内看不到。

### 方案

- 新增通用事件 `ReportCacheEvictEvent`（`snowy-common`），携带 `tenantId` 和来源；
- 收款（订单支付/线下收款）、退费完成、点名消课成功后发布事件；
- 财务侧用 `@TransactionalEventListener(phase = AFTER_COMMIT, fallbackExecution = true)` 监听，
  切换租户上下文后清掉该租户 `report:` 前缀的缓存；
- 缓存 TTL 从 300 秒降到 60 秒，只作为事件丢失时的兜底。

事务提交后再清缓存，避免“事务还没提交就清、清完又被旧数据填回去”。

验证：先读一次汇总（`paidAmount=57600`），再线下收款 1234.56，立即再读 → `58834.56`、订单数 16 → 17。

## 二、招生漏斗口径单调 + 查询瘦身

### 问题

- 「已试听」= 状态为已试听/已报名 **或** 区间内存在试听预约；
  「已跟进」= 状态为跟进中及以上 **或** 存在跟进记录。
  一条新线索被约了试听（或状态被改回新线索），就会出现「已试听 > 已跟进」的倒挂。
- 漏斗为了数几个阶段，把区间内所有线索的全部字段读进内存。

### 方案

- 逐级收窄：`已报名 ⊆ 已试听 ⊆ 已跟进 ⊆ 新线索`。
  已报名同时计入已试听与已跟进，已试听计入已跟进，保证漏斗永远单调递减；
- 线索只查 `ID/STATUS`，跟进记录与试听预约只查 `LEAD_ID`；
- 来源渠道报表同样只查 `ID/SOURCE/STATUS`。

验证：演示数据漏斗 `新线索 23 > 已跟进 1 > 已试听 0 > 已报名 0`，单调性检查通过。

## 三、KPI 环比

新增 `KpiDelta` 组件与 `reportCompare` 工具：

- `previousRange(start, end)` 按当前区间长度算出紧邻的上一周期（例如 10/22–10/23 → 10/21–10/21）；
- 卡片下方显示「较上期 +12.3%」，上涨绿色、下跌红色；
- 支持 `invert`：退费、缺勤、退费率这类「涨了是坏事」的指标反向着色；
- 上期为 0 时不显示，避免出现无意义的百分比。

已接入：

| 页面 | 指标 |
|---|---|
| 财务报表 | 收款、退费、净营收、课消金额、订单数、客单价、退费率 |
| 教务报表 | 到课、请假、缺勤、应到、到课率 |
| 招生报表 | 线索量、已报名、报名转化率、试听数、试听报名数、试听转化率 |

环比数据只用于展示，失败不影响主报表加载。
