# 启动迁移阶段化

上一轮解决了「迁移失败被静默吞掉」，本轮处理剩下的「顺序靠数字间距」问题。

## 一、原状况

12 个启动迁移监听器各自返回一个魔数：

| 顺序值 | 迁移 |
| --- | --- |
| `LOWEST_PRECEDENCE - 20` | P0SchemaMigration |
| `- 15` | PlatformOpsSchemaMigration、StudentArchiveSchemaMigration、StudentRenewWarnSchemaMigration、CrmPermissionMigration |
| `- 14` | CourseSchedulePermissionMigration、FinancePermissionMigration、StudentArchivePermissionMigration、StudentRenewWarnPermissionMigration |
| `- 13` | CourseClassTypeSchemaMigration |
| `- 10` | PlatformBootstrap |
| `LOWEST_PRECEDENCE` | DevJobListener、TenantIsolationAudit |

三个问题：

1. **同值项顺序未定义**。`-15` 挤了 4 个、`-14` 挤了 4 个，Spring 对相同 order 的处理顺序不保证，依赖它们之间的先后就是靠运气。
2. **新增迁移只能靠挑数字**。想插到 `-15` 和 `-14` 之间就得发明 `-15.5` 或用更小的间隔，没有任何约束，改错不会报错。
3. **注释引用具体数字**。比如「晚于 P0SchemaMigration（LOWEST_PRECEDENCE - 20）」，一旦调整就全部失效。

## 二、阶段链

新增 `StartupPhase`（`snowy-common`），把顺序收敛成一条推导链：

```java
BASE_SCHEMA         = LOWEST_PRECEDENCE - 7 * STEP    // 底座结构
PLATFORM_SCHEMA     = BASE_SCHEMA + STEP              // 平台结构
DOMAIN_SCHEMA       = PLATFORM_SCHEMA + STEP          // 业务域结构
DOMAIN_PERMISSION   = DOMAIN_SCHEMA + STEP            // 业务域权限
PLATFORM_BOOTSTRAP  = DOMAIN_PERMISSION + STEP        // 平台账号初始化
AUDIT               = PLATFORM_BOOTSTRAP + STEP       // 启动自检
TIMER_START         = AUDIT + STEP                    // 定时任务启动
```

`STEP = 1000`，每一级由上一级推导，**结构上不可能出现取值冲突**。同一阶段内的多个迁移视为相互独立；若确实存在依赖，应拆到不同阶段。

顺序依据：

- 结构调整必须在权限登记之前——权限会引用表与菜单，表还没建好就登记会指向空对象；
- 账号初始化在权限之后——保证菜单授权覆盖本次新增菜单；
- 自检在全部就绪之后——否则会误报未登记；
- 定时任务最后——避免结构未就绪就触行业务逻辑。

## 三、一个测试抓到的真实缺陷

首版把起点写成 `LOWEST_PRECEDENCE - 6 * STEP`。链上共 6 次递增，`TIMER_START` 正好算到 `LOWEST_PRECEDENCE` 本身，与「所有阶段都必须早于 LOWEST_PRECEDENCE」的前提冲突。

`StartupPhaseTest` 立刻报出：

```
StartupPhaseTest.allPhasesBeforeLowestPrecedence:83 expected: <true> but was: <false>
```

把起点改为 `- 7 * STEP` 后通过。这个缺陷在原来的魔数写法里完全不可见——因为没人会去算 `-20` 是否紧贴下界。

## 四、调试中踩到的构建坑

修完常量后测试仍然失败，排查过程值得记录：

单独执行 `mvn -pl snowy-web-app test` 时，web-app 从**本地仓库**取插件 jar，而不是 reactor 里的最新产物。因此：

- 新增的类（如 `RefundAmountCalculator`）会报「程序包不存在」；
- 修改过的常量（`StartupPhase`）会读到旧值，表现为「代码明明是新的，断言就是不通过」。

正确做法是全仓 `clean install`，或至少 `clean package` 全量构建。这也是 `docs/` 里早先记录的构建坑的又一次复现——单独构建 web-app 依赖仓库里的旧插件 jar。

同样地，`rm -f` 可执行包后只跑 `-pl snowy-web-app package`，打出来的包里缺 `sa-token` 等依赖（`NoClassDefFoundError: SaServletFilter`），必须全量打包。

## 五、验证

**单元测试**（`StartupPhaseTest`，6 个用例）：

- 阶段严格递增（7 级逐级比较）；
- 结构调整早于权限登记；
- 自检在全部结构与权限之后；
- 定时任务在自检之后；
- 所有阶段早于 `LOWEST_PRECEDENCE`；
- 阶段间距留有细分余量。

**实际启动顺序**（从日志时间戳确认）：

```
13:53:26  P0SchemaMigration              (底座结构)
13:53:31  PlatformOpsSchemaMigration     (平台结构)
13:53:32  StudentArchiveSchemaMigration  (业务域结构)
13:53:33  StudentArchivePermissionMigration (业务域权限)
13:53:36  PlatformBootstrap              (账号初始化)
13:53:37  TenantIsolationAudit           (自检)
```

为确认权限阶段确实在调度中，刻意删除一条权限资源后重启，日志出现「学员档案权限升级：资源 1」，资源总数恢复为 107。之前看不到权限迁移日志，是因为它们幂等且无变更时不打印——不是没执行。

**汇总输出**：`>>> 启动期结构/权限迁移全部成功`、`>>> 租户隔离自检通过：含 TENANT_ID 的 50 张业务表均已登记`。
